# Fixly CRM — З чого почати

Цей файл — практичний покроковий план перших дій, окремо від `TODO.md`
(який більше про повний чеклист фіч). Тут — саме про те, у якому порядку
сідати і що робити в перші дні/тижні, щоб не загубитись.

## Крок 0. Підготовка репозиторію (30–60 хв)

1. Створи папку `fixly-crm/`, а в ній `frontend/`, `backend/`, `docs/`. ✔
2. `git init`, перший commit із порожньою структурою. ✔
3. Поклади файли `project.md`, `database.md`, `api.md`, `ui.md`, `TODO.md` ✔
   у `docs/` — вони тепер твоя "єдина правда" про проєкт, звіряйся з ними,
   коли забуваєш деталі.

## Крок 1. Backend "скелет" без бізнес-логіки (день 1–2)

Мета — просто підняти сервер і базу, без жодної реальної фічі.

1. `cd backend && npm init -y` ✔
2. Встанови Express: `npm install express` ✔
3. Встанови PostgreSQL локально (або підніми через `docker run postgres`).
4. Встанови Prisma: `npm install prisma --save-dev` і `npm install @prisma/client`
5. `npx prisma init` — це створить `prisma/schema.prisma` і `.env`
6. Пропиши в `.env` рядок `DATABASE_URL`, підключись до своєї бази.
7. Зроби мінімальний `server.js` з одним роутом `GET /health`, який повертає
   `{ status: "ok" }`. Запусти, перевір у браузері/Postman.

**Чекпоінт:** сервер стартує, `/health` відповідає, Prisma підключена до
живої PostgreSQL бази.

## Крок 2. Схема бази даних (день 2–3)

1. Відкрий `docs/database.md` і перенеси моделі `Business`, `User`,
   `Customer`, `Service`, `Appointment` у `prisma/schema.prisma`.
2. Прописуй зв'язки по одному — спочатку `Business ↔ User`, зроби міграцію,
   перевір у Prisma Studio (`npx prisma studio`), що все як очікувалось.
   Потім додай наступну модель і так по черзі — не пиши всю схему одразу.
3. Коли всі 5 моделей на місці і зв'язки правильні — зроби фінальну
   `npx prisma migrate dev --name init`.

**Чекпоінт:** у Prisma Studio видно всі 5 таблиць з правильними зв'язками.

## Крок 3. Авторизація — перший наскрізний функціонал (день 3–5)

Це найважливіший крок, тому що саме тут закладається мультитенантність.

1. Backend: `POST /api/auth/register` — приймає `businessName, name, email,
password`, створює `Business` і `User` з роллю `admin` **в одній
   транзакції** (`prisma.$transaction`).
2. Захешуй пароль через `bcrypt` перед збереженням.
3. `POST /api/auth/login` — перевіряє пароль, видає JWT (access token),
   поклади його в httpOnly cookie.
4. Напиши middleware `authenticate`, який читає токен, дістає `userId` і
   `businessId`, кладе їх у `req.user`.
5. Створи один тестовий захищений роут (`GET /api/auth/me`), щоб перевірити,
   що middleware працює.
6. Тільки після цього переходь на frontend: сторінки `/register`, `/login`,
   `ProtectedRoute`.

**Чекпоінт:** можеш зареєструватись через UI, залогінитись, і захищена
сторінка (поки що пуста) відкривається тільки з валідним токеном.

## Крок 4. Перша повна CRUD-фіча — Customers (день 5–8)

Зроби **саме одну** сутність повністю, від backend до frontend, перш ніж
братися за наступну. Це задасть шаблон, який ти повториш для Services і
Appointments.

1. Backend: контролер + роути для Customers, обов'язково з фільтром
   `where: { businessId: req.user.businessId }` у кожному запиті.
2. Перевір вручну (Postman/Thunder Client): створи двох різних "бізнесів"
   через `/register`, і переконайся, що клієнти одного не видно іншому.
   Це найкритичніша перевірка в усьому проєкті — зроби її зараз, поки
   структура ще проста.
3. Frontend: RTK Query slice для customers, сторінка списку, форма
   створення/редагування, підключення до backend.

**Чекпоінт:** повний цикл — реєстрація → логін → CRUD клієнтів у браузері,
з ізоляцією даних між бізнесами.

## Головні правила по дорозі

- **Не пиши весь backend наперед.** Роби вертикальний зріз: одна модель →
  її роути → її frontend → перевірка руками → наступна модель.
- **Мультитенантність перевіряй одразу**, як тільки з'являється друга
  сутність з `businessId` (Крок 4), а не в кінці проєкту.
- Якщо застряг більш ніж на годину на одній дрібниці — переходь до
  наступного пункту і повертайся пізніше, не блокуй весь прогрес.
- Звіряйся з `docs/database.md`, `docs/api.md`, `docs/ui.md` кожного разу,
  коли не пам'ятаєш, яке саме поле/роут/сторінка мала бути — це і є їхнє
  призначення.
